## 2. Critical schema differences: real BotWorldState versus current JoshRS fixture

Read from [PR #62 fixture](https://github.com/Parris-Tech-Services/JoshRS/blob/feature/rs377-rssdk-claude-harness-20261102/tools/rs377-agent-harness/src/fixture-transport.mjs) and [guard](https://github.com/Parris-Tech-Services/JoshRS/blob/feature/rs377-rssdk-claude-harness-20261102/tools/rs377-agent-harness/src/guard.mjs):

- **These are not the same structure.** JoshRS fixture nests everything under `world` and `player`, with `player.username`, `plane`, `xp: {Woodcutting: 0}`, `inventory[].quantity`, `questStages` and `dialogue`. RS-SDK expects `player.name`, `player.level` for plane, `player.worldX/worldZ`, top-level `skills[]` with `experience`, top-level `inventory[]` with `count`, and top-level `dialog` and other UI fields.
- **Protocol revision vs publication revision:** `fixture.world.revision === 377` expresses the JoshRS test-world game version; SDK `state.revision` means *publication sequence number*. Never equate them. Keep authoritative 377 world/tick/identity separately in an authenticated transport envelope or trusted side-channel; do not assume upstream SDK world state proves these.
- **Quest progress absent from declared SDK world state:** `questStages` is not a defined `BotWorldState` property at this pin. Preserve it as a separate read-only JoshRS bot-specific result/extension with documented provenance, rather than pretending the upstream SDK provides quest completion.
- **NPC targets:** a type/config `id` is NOT an entity `index`; the SDK `interactNpc` action addresses `npcIndex`. Locations require their observed `level`/plane and fresh option/index choice; dialogue `clickDialogOption` can carry a guard `{pageId, componentId}` that MUST be checked atomically or refused.
- **Truthful observation:** do not produce blank or fabricated nearby NPC, bank, shop, equipment or quest fields and describe it as full SDK integration. For fields the rev-377 adapter genuinely cannot yet observe, mark coverage unsupported in a separate capability ledger and gate affected actions until implemented; any neutral defaults must be explicitly justified, not invented live evidence.
- **Existing action translator:** [`rssdk-actions.mjs` in draft PR #62](https://github.com/Parris-Tech-Services/JoshRS/blob/feature/rs377-rssdk-claude-harness-20261102/tools/rs377-agent-harness/src/rssdk-actions.mjs) maps just eight normal action variants. It validates basic shape and performs renaming; it neither owns the native 377 packet codec, nor sends packets, nor operates the upstream WebSocket, nor observes the real player. It deliberately rejects guarded dialogues. *Do not mistake translator round-trip tests for live protocol compatibility.*

## 3. Four message legs to implement and validate

1. **JoshRS #377 client-session adapter → gateway:** authenticate a dedicated ordinary rev-377 bot through actual RSA/ISAAC client login; separately register its authenticated sidecar session with `{type:'connected', username, password, clientId}`. Publish real read-only `{type:'state',state:BotWorldState}` updates with proven identity/tick provenance. Never use a human account or copy `private.pem`.
2. **Unmodified upstream SDK → gateway:** `new BotSDK({botUsername, password, gatewayUrl, connectionMode:'observe', autoLaunchBrowser:false, readyTimeout:0})`; call `connect()`, check `isAuthenticated()`, `getState() !== null` and fresh `getStateReceivedAt()` **separately**. It sends `sdk_connect` and receives `sdk_connected`, `sdk_state`. For a controlling disposable bot only, opt into `connectionMode:'control'` after controller-lease safety proof.
3. **SDK action → bot:** `sdk_action` carries `actionId`, typed `BotAction` and deadline; gateway sends bot `action` with the same ID. The adapter must validate identity/allowlist/arguments, translate into **normal rev-377 packets** and never call server methods to grant XP, items, quests or teleports.
4. **Bot observed result → SDK:** bot responds `actionResult` with original `actionId` and explicit `phase`, while independently sampled `state` reveals effects. An acknowledgement alone is `dispatch`, not `completion`. Correlation, stale-state, timeout, cancellation and reconnect behaviour must be tested with actual upstream `BotSDK` before claiming compatibility.

**Important:** `connect()` may resolve even after `waitForReady` fails: [index 349–367](https://github.com/MaxBittker/rs-sdk/blob/db0cc51e0a8f9f0d6a7d60c44e534412bb0601bb/sdk/index.ts#L349-L367). `getStateAge()` returns **0 if no state has ever been received**, so zero does *not* prove freshness: [index 709–721](https://github.com/MaxBittker/rs-sdk/blob/db0cc51e0a8f9f0d6a7d60c44e534412bb0601bb/sdk/index.ts#L709-L721). Demand a non-null state plus positive receive timestamp and monotonic update proof.

## 4. Gateway defaults and other genuine security hazards

**Do not run upstream gateway with its defaults on a reachable interface.**

- Upstream `GATEWAY_HOSTNAME` defaults to `0.0.0.0`, **not loopback**, and `LOGIN_SERVER` defaults disabled. With `LOGIN_SERVER !== 'true'`, `authenticateSDK()` returns `success:true` for any username/password. See [gateway 22–25](https://github.com/MaxBittker/rs-sdk/blob/db0cc51e0a8f9f0d6a7d60c44e534412bb0601bb/server/gateway/gateway.ts#L22-L25) and [53–54,105–109](https://github.com/MaxBittker/rs-sdk/blob/db0cc51e0a8f9f0d6a7d60c44e534412bb0601bb/server/gateway/gateway.ts#L53-L54). Never assume a nonempty password on the SDK client enforces server-side auth.
- `control` is last-writer-wins: new controller forcibly closes existing controller sessions, and reconnects can pre-empt. `observe` is non-pre-empting, but **not strict read-only** because gateway's implementation permits public chat and private messages ([gateway 582–635](https://github.com/MaxBittker/rs-sdk/blob/db0cc51e0a8f9f0d6a7d60c44e534412bb0601bb/server/gateway/gateway.ts#L582-L635)). Implement a JoshRS-specific no-chat strict observer role or disable all action emission at adapter boundary; do not use `observe` as a security boundary.
- A second bot-client `connected` with the same username can ask the old session to save/disconnect, with a five-second forced close fallback ([gateway 405–432](https://github.com/MaxBittker/rs-sdk/blob/db0cc51e0a8f9f0d6a7d60c44e534412bb0601bb/server/gateway/gateway.ts#L405-L432)). Never connect to Elrothiro, Sylvie, Luna or an active worker identity.
- Upstream MCP `execute_code` can load a repo-relative or absolute module path ([execute-code 100–110](https://github.com/MaxBittker/rs-sdk/blob/db0cc51e0a8f9f0d6a7d60c44e534412bb0601bb/mcp/execute-code.ts#L100-L110)) and runs model-supplied code. Do not expose it unsandboxed. Instead provide **bounded typed no-cheat tools** and OS sandboxing for any future script-execution workflow.
- A safe deployment needs loopback-only gateway binding **and** server-side authentication/authorization, per-bot controller ownership, private transport if remote, zero credential logging, explicit consent for world access, rate limits and no accidental human-account takeover. A private LAN/Tailscale tunnel alone does not make an unauthenticated gateway safe.

## 5. What the current JoshRS source actually provides

- On **main**, [`tools/rs377-bot-bench/fred-george-family-client.mjs`](https://github.com/Parris-Tech-Services/JoshRS/blob/main/tools/rs377-bot-bench/fred-george-family-client.mjs) implements a narrow #377 login / keepalive / hard-coded movement example (ISAAC, RSA, opcode 40 `NO_TIMEOUT`, opcode 28 `MOVE_GAMECLICK`). Its `HOST = '127.0.0.1'`, fixed port fallback and local `private.pem` read **must not be copied directly for a Fedora remote bot**. It drains server packets rather than decoding full client-visible world state.
- On **draft PR #62**, the [harness](https://github.com/Parris-Tech-Services/JoshRS/tree/feature/rs377-rssdk-claude-harness-20261102/tools/rs377-agent-harness) provides eight-action type guards, read-only *fixture* observations, mapper and source-only tests. The fixture `world.mode='isolated'` and `revision=377` are test metadata, **not** cryptographic or authoritative proof of a correctly configured game server.
- The existing source-only handoff is correct in **overall approach** but should be read with the specific security and schema corrections above. Neither current code path proves a genuine `BotSDK.getState()` with real rev-377 fields, `sendWalk()` to real login, an observed tree chop, or two characters in the exact server Elrothiro uses.

## 6. Recommended implementation seam (minimal, non-disruptive)

**Preferred boundary:** genuine ordinary #377 bot client session for authentication + permitted actions; trusted bot-only read-only observation service for genuine game state; a separate loopback-authenticated **gateway protocol adapter** exposing the pinned SDK wire format. Prefer a minimal isolated, authenticated gateway-compatible implementation over starting the upstream gateway with its unsafe defaults. Only use the upstream gateway itself if explicitly configured and tested for login-server auth, bind, takeover and data isolation.

Acceptance gates for the next owner (not completed by this audit):

1. Static **type contract**: TypeScript type-check against the pinned actual `sdk/types.ts` / `BotAction` rather than using a homegrown type called `BotWorldState`.
2. **Transport smoke**: actual upstream `BotSDK` connects in observe-only mode, sees a genuine changing bot state, and disconnects without affecting another controller; test auth failure and wrong bot.
3. **Legal input:** on a disposable rev-377 instance, an SDK-issued walk/NPC/loc action causes the correct normal client packet, with no direct server mutation.
4. **Observed effect:** independently verify a destination coordinate and a newly obtained log plus natural XP gain across genuine ticks; no faux success when only an ACK is returned.
5. **Identity/persistence:** same authoritative world as Elrothiro verified via independent live observations; separate bot save/logout/relogin and no interruption to existing player sessions. Explicit approval required before accessing production.
